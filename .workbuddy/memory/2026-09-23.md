## macOS 桌面客户端打包体检（基于 071e77c / desktop-nas 分支 c243ef9, v2.3.0.0）

**任务**：分析当前「打包成客户端」的实现（desktop.py + desktop.spec + GitHub Action）在 macOS 上的问题。
**结论**：当前打包产物**无法启动**，且前端「下载」核心链路在 macOS 上失效。

### 实测证据（不是推测）
- 用 `cd / && open /tmp/ud_dist/UniversalDownloader.app` 复现真实双击：进程秒退。
  日志：`OSError: [Errno 30] Read-only file system: '/downloads'`，
  栈：`desktop.py:13 → main.py:251 → downloader/__init__.py:1 → server_downloader.py:16 os.makedirs(DOWNLOAD_DIR)`。
- 根因：`server_downloader.py:15` 用 `os.getcwd()/downloads` 作为下载根目录，且在 **import 期** `os.makedirs`。
  Finder 双击时 cwd=`/`，`/` 只读 → import 失败 → 整个 App 起不来。
  且 `desktop.py` 的 `os.chdir(sys._MEIPASS)` 在第 13 行 `from main import app` **之后**才执行，救不了。
- pywebview 6.2.1 源码证据：`webview/__init__.py:120 'ALLOW_DOWNLOADS': False`；
  `platforms/cocoa.py:279 / :339` 用它做门禁。desktop.py 从未开启 →
  前端 `URL.createObjectURL` + `a.download`（app.js:1118-1126）在 WKWebView 里走
  "Normal navigation, allow"（cocoa.py:320-322），会把主框架导航到 blob，
  即「点下载后整页 UI 被替换，且没有返回按钮」。
- pywebview 6.2.1 源码证据：`__init__.py:139 'private_mode': True`（默认）。
  `desktop.py` 未传 → `cocoa.py:632-644` 每次都清空 website data →
  **localStorage 不落盘**，B站 SESSDATA（app.js 存 localStorage）每次重启丢失。
- 构建日志：`DEPRECATION: Onefile mode in combination with macOS .app bundles ... will become an error in v7.0`；
  `EXE target arch: arm64`（不是 Universal）；`CFBundleShortVersionString => 0.0.0`；图标是 PyInstaller 默认 icns；签名为 adhoc / TeamIdentifier 未设置。
- `webview.open('...','_blank')`（app.js:518 图集看原图）在 cocoa.py:261-269 会落到
  `webview.loadRequest_` → 同样把主界面替换成一张图。

### 修复方向（已在 /tmp/ud_probe 临时副本实测通过）
1. `downloader/server_downloader.py`：`DOWNLOAD_DIR` 改为稳定的用户目录（macOS: `~/Downloads/UniversalDownloader`），
   并去掉 import 期 `os.makedirs`（挪到 `ServerDownloadManager.__init__` 里 try/except）。
2. `desktop.py`：删掉 `os.chdir(sys._MEIPASS)`；`webview.settings['ALLOW_DOWNLOADS'] = True`；
   `webview.start(debug=False, private_mode=False, storage_path=~/Library/Application Support/UniversalDownloader)`。
3. `desktop.spec`：改 ONEDIR；补 `CFBundleShortVersionString`；换成自制 icns；`upx=False`。
4. 建议把「下载」改成走 `DesktopAPI` 原生落盘（`choose_folder`/`open_path` 已写好但前端从未调用，
   属死代码），而不是依赖 webview 下载。
5. 注意坑：用环境变量 `DOWNLOAD_DIR` 传下载根目录会让 `/api/server/config` 的
   `is_nas_mode` 变成 true，前端会默认切到「NAS/服务端归档」。要单独区分桌面模式。

实测：修复版重新构建后 `open` 启动成功，`/health`、`/`、`/static/js/app.js`、
`/api/server/config` 全部 200 正常。产物在 `/tmp/ud_dist2/UniversalDownloader.app`（未落进仓库）。

### 实测证据
- `open`（真实双击，cwd=/）启动成功；端口固定 18760；`/health` `/` `/static/*` `/api/local/config` `/api/server/config` 全 200
- 端到端下载：图片 / 普通视频（自动落 `回归合集/` 子目录）/ ffmpeg 混流 三个任务 **100% 成功**；
  产物字节数与源文件完全一致；混流产物经 ffmpeg 校验确含 `h264` 视频轨 + `aac` 音轨
- 二次启动日志出现「检测到同版本实例已在运行，复用其后端」

### 关键教训（务必记住）
**WebView 的 localStorage / Cookie 按「源」(scheme://host:port) 隔离。**
原实现每次启动都用随机端口 → 每次都是新源 → **即使开了 `private_mode=False` 设置照样丢**。
实测：7 次启动产生 7 个互不相通的源存储；改成固定端口后只剩 1 个源，重启后值仍在。
结论：只修 `private_mode` 是不充分的，必须同时固定端口（或把设置放到后端）。

### 沙箱测试坑
`open` / 子进程会继承 shell 的 `HTTP_PROXY`，httpx 默认 `trust_env=True`，
连 `127.0.0.1` 都会被送进代理 → 出现莫名其妙的 502/503。
→ 本地端到端测试要 `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy`。

### 实测暴露的真缺陷（已修）
1. `_download_track` 原先只在 **4xx/5xx** 时换源，**连接失败（主机不可达）不换源** ——
   而 CDN 故障最常见的就是连不上。现同时捕获 `httpx.HTTPError` 后换源。
2. `desktop.py` 启动时**无条件**对包内 ffmpeg `chmod`（打包时已带 +x），
   实测该调用被沙箱文件写拦截**挂住整个进程**（sample 显示栈停在 `os_chmod_impl`），
   在只读安装位置（/Applications）也必然失败。改为 `os.access(X_OK)` 判断后按需 chmod。

沙箱教训：`timeout` 在 zsh 下不存在（用 `gtimeout` 或后台+kill 兜底）。
